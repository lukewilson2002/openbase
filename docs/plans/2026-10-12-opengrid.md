# OpenGrid Plan

**Goal:** A self-hosted, fully featured Airtable alternative for individuals and very small businesses, with a Rust backend and a TypeScript frontend, that runs reliably on a $4–6/month VPS.
**Approach:** One Rust binary (axum + SQLite) serves a JSON API and embeds a prebuilt React + TypeScript single-page app. A pure-Rust core crate (field types, formula engine, filter/sort semantics) is authoritative on the server; its API DTOs are exported to TypeScript with ts-rs so the client is type-checked against the server contract. Computed fields are materialized in SQLite and kept current by a dependency-graph recompute engine; views are queried by streaming rows through the core filter/sort code with a small result cache.
**Stack:** Backend: Rust 2024, axum 0.8, tokio, rusqlite 0.40 (bundled SQLite 3.53, WAL), argon2, totp-rs, lettre + reqwest (rustls, no OpenSSL), image, rust-embed, chrono/chrono-tz, croner, ts-rs. Frontend: TypeScript (strict), React 19, Vite, Glide Data Grid (grid), TanStack Query, React Router, Radix UI primitives + Tailwind CSS v4, dnd-kit (kanban), FullCalendar standard MIT plugins (calendar), lucide-react, marked + DOMPurify; Vitest + Testing Library, Playwright (E2E).
**Research:** `docs/research/` (Airtable inventory, Baserow and peers, Rust crate stack, frontend tradeoffs).
**License:** MIT OR Apache-2.0. No paid tier, no license keys, no feature flags gating anything.

## 1. Decisions

### 1.1 Frontend: React + TypeScript (changed 2026-10-12 at the owner's request)

**History.** The original brief said "write it all in Rust", and the first version of this plan chose Leptos (Rust → WASM) while stating plainly that a TypeScript frontend would be the better engineering choice: an Airtable clone's frontend is ~70% complex interactive widgets (spreadsheet grid with range selection, fill handle and paste; kanban drag-and-drop; calendar; timeline; pickers) that exist MIT-licensed and battle-tested in the JS ecosystem and do not exist in Rust. Rust/WASM speed was never the problem; ecosystem maturity, hand-building every widget, and pre-1.0 framework churn were. After reading that, the owner switched the frontend to TypeScript. **The backend stays 100% Rust.**

**Decision: React 19 + TypeScript (strict) + Vite.** Why React rather than Svelte, Vue or Solid: the libraries this product needs most (Glide Data Grid, Radix UI, TanStack Query, dnd-kit, FullCalendar) are React-first; it has the largest contributor pool for an open-source project; and the closest open-source peer (Teable) proves the exact stack (React 19 + Glide) for an Airtable clone. Svelte 5 or Solid would be leaner but would force us to hand-build or wrap the grid, which is the one component we most want off the shelf.

| Concern | Choice | Why |
|---|---|---|
| Grid | **Glide Data Grid 6.x** (MIT, canvas) behind our own `GridAdapter` interface | Only OSS grid with range selection, fill handle, copy/paste, column resize/reorder and frozen columns built in; canvas scrolls smoothly at 100k rows. **Risk:** last stable release is 6.0.3 (Feb 2024) and its peer range says React ≤18; Teable runs it on React 19. Mitigation: pin exactly, use npm `overrides` for the peer range, keep it behind `GridAdapter` so it can be vendored or replaced. **Fallback** if it misbehaves on React 19: our own DOM grid on TanStack Virtual (MIT, very active). |
| UI primitives | Radix UI + Tailwind CSS v4, components copied into the repo (shadcn/ui pattern) | Accessible dialogs, menus, popovers and selects with no runtime vendor lock-in; Tailwind v4 needs no PostCSS config. |
| Server state | TanStack Query | Caching, refetch, optimistic updates; SSE events simply invalidate queries. |
| UI state | React state/context; Zustand only for the grid selection/undo stores | Keep global state small. |
| Routing | React Router (library mode) | Stable, simple. |
| Kanban DnD | dnd-kit | Mature, accessible (keyboard drag). |
| Calendar | FullCalendar MIT plugins only (daygrid, timegrid, interaction) | Month/week views and drag-reschedule for free; premium plugins are never used. |
| Timeline / Gantt | Custom SVG component | No MIT library offers swimlanes + dependency arrows in a shape we want; the scope (bars, lanes, arrows, drag) is moderate. |
| Rich text | marked + DOMPurify (sanitized markdown) | Long-text "rich" fields are markdown; sanitization prevents XSS. |
| Contract | ts-rs generates TypeScript types from `og_core::api`, `field`, `view` | A Rust DTO change breaks the TypeScript build instead of breaking production. CI checks the generated files are current. |
| Tests | Vitest + Testing Library (units/components), Playwright (E2E) | Standard, well-supported. |

**Cost of this choice:** a second language and Node in development and CI, plus npm supply-chain exposure. Mitigations: a small dependency allow-list, committed `package-lock.json`, `npm ci --ignore-scripts`, no runtime CDN. **Self-hosters never install Node**: the Docker build and release binaries embed the built assets; the server is still one binary.

**What we gave up:** running the Rust formula engine in the browser for instant previews. Instead the server exposes a formula check endpoint (`POST /api/tables/{id}/formula/check`) that parses, type-checks and previews a formula against a sample record.

### 1.2 Database: SQLite, one file

SQLite (bundled, WAL mode) in a single `opengrid.db` file, plus an `attachments/` directory. Rationale: zero extra processes or memory (Postgres would need ~100+ MB and its own upgrades — Baserow's Postgres 11→15 upgrade broke installs), backups are a file copy (`VACUUM INTO`), and a small business never approaches SQLite's write limits. One writer connection serializes writes (no `SQLITE_BUSY` storms); a pool of 4 read-only connections serves queries concurrently.

Considered and rejected: **one SQLite file per base** (Grist-style). It gives per-base backup and blast-radius isolation, but costs cross-file migration logic, connection management per base, and cross-base user/permission joins. A single file is simpler to operate and back up at this scale.

### 1.3 Storage model: JSON rows + materialized computed values

User tables are **not** real SQL tables. Each record is one row in `records` with a JSON `data` object keyed by **field id**. Consequences:

- Adding/renaming/deleting fields never runs DDL; deleting a field is metadata-only (restorable from trash because the data is still in the JSON).
- No dynamic SQL from user input anywhere (eliminates a whole injection class).
- Field type changes rewrite values in one transaction (chunked if large).

**Computed fields (formula, lookup, rollup, count) are materialized** into the same JSON on write, by a recompute engine driven by a field dependency graph (same-table refs and cross-table refs through link fields). Rationale (from Baserow's experience and our RAM budget): computing on read would require loading linked tables into memory for every sort/filter. Cycles are rejected when a field is created/changed. Volatile formulas (`NOW()`, `TODAY()`) are refreshed by a background tick every 5 minutes. Created/modified time/by and autonumber come from record columns.

Links: every link field has a paired inverse field in the linked table (self-links included); both sides store record id arrays, kept consistent in the same transaction. The inverse side doubles as the reverse index for cascade recompute and delete cleanup.

**View queries**: stream the table's live rows from SQLite, evaluate the view filter and search in Rust (the same `og-core::query` code the browser has), compute sort keys, sort, then page. The ordered id list is cached per (view config, search, table version); writes bump the version. Page fetches after the first are an id lookup.

### 1.4 Real-time collaboration: IN (live updates, last-write-wins per cell)

Server-Sent Events per base (`GET /api/bases/{id}/events`) from an in-process `tokio::sync::broadcast` channel. Events are invalidation hints (record ids, schema changed); clients refetch what they display. Conflicts: last write wins per cell; there is no OT/CRDT, so two people typing in the same long-text cell at once will overwrite each other (the record history keeps both versions). Cost: one long-lived HTTP connection per open tab and ~1 KB per subscriber; no Redis, no extra process. Presence avatars and live cursors: **cut** (low value, adds a client→server channel).

### 1.5 Realistic scale limits

Targets for a 1 vCPU / 1 GB VPS (to be verified by `crates/server/tests/scale.rs`, which seeds 50k records; numbers in the README must come from that test):

| Limit | Value | Enforced |
|---|---|---|
| Records per table | **50,000 comfortable**, 100,000 hard cap | hard cap in `og_core::limits` |
| Fields per table | 500 | hard |
| Tables per base | 200 | hard |
| Concurrent active users | ~25 (SSE connections: a few hundred) | not enforced |
| Upload size | 100 MB per file (configurable) | hard |
| Grid page fetch (cached) | < 50 ms p95 at 50k rows | test |
| View re-query after a write | < 1 s at 50k rows, < 100 ms at 5k | test |
| Process RSS | < 60 MB idle, < 300 MB under load at 50k rows | measured |

### 1.6 Other decisions

- **Dates:** chrono + chrono-tz (croner requires chrono anyway; one date library). Instants are stored UTC; date-only values as `YYYY-MM-DD`.
- **Auth:** Argon2id (m=19 MiB, t=2, p=1; at most 2 concurrent hashes), opaque server-side session tokens (only SHA-256 stored), HttpOnly + SameSite=Lax + Secure (when public URL is https) cookies, optional TOTP 2FA, invite-only signup by default (first user becomes admin), per-IP rate limits on login/signup/reset/forms.
- **CSRF:** cookie-authenticated unsafe requests must carry `X-OpenGrid-CSRF: 1`; no CORS is ever enabled, so cross-site pages cannot add it.
- **TLS:** terminate at Caddy (automatic HTTPS) in the shipped docker-compose; OpenGrid itself speaks HTTP on localhost.
- **Undo/redo:** client-side stack of inverse operations (cell edits, record create/delete, field delete → restore from trash). No server action log.
- **E2E browser tests:** Playwright (TypeScript) in `web/e2e`, run against a real `opengrid` binary on a temp data dir.

## 2. Scope: BUILD vs CUT

### BUILD

**Accounts & admin.** First-run setup (first user = admin); invite-only or open signup; login/logout; session list and revoke; password change; password reset (email when SMTP is configured, otherwise admin-generated reset link or `opengrid reset-password`); TOTP 2FA; profile + timezone; personal access tokens (read/write, optionally limited to bases). Admin: users (create, deactivate, promote, reset link), instance stats, audit log, backups (list, create now, download).

**Workspaces & sharing.** Workspaces with members and roles (owner, creator, editor, commenter, viewer); invites by link (and email if SMTP); base-level sharing (effective role = max of workspace and base role); read-only view share links (optional password); public form links.

**Bases, tables, fields.** Create/rename/color/icon/duplicate (with or without records)/delete/restore bases and tables. 28 field types: single line text, long text (plain or markdown rich text), number, currency, percent, duration, rating, checkbox, single select, multiple select, date (optional time, formats, per-field or viewer timezone), email, URL, phone, attachment (thumbnails), link to another record (paired, optional single-record, picker limited to a view), user (single/multiple, notify), formula, lookup, rollup, count, created time, last modified time (optionally watching specific fields), created by, last modified by, autonumber, barcode (stored as text), button (open URL from formula). Field descriptions, defaults, type conversion with data conversion, primary field change, delete/restore.

**Formula language.** Airtable-compatible syntax and the full 84-function list from `docs/research/airtable-features.md` §3.1 including Moment-style `DATETIME_FORMAT`, `DATETIME_DIFF`/`DATEADD` units, `SET_TIMEZONE`, `WORKDAY(_DIFF)`, regex functions (linear-time `regex` crate). Rollups are formulas over `values`. `SET_LOCALE` accepted but only English output (see cuts).

**Records.** Create/edit/delete/restore, batch operations, manual ordering, expand record, duplicate, comments with @mentions, per-record revision history, attachments, copy/paste ranges, fill handle, undo/redo, search.

**Views (all 7 Airtable base view types, Gantt as a Timeline mode).** Grid; Form; Gallery; Kanban (stack by single select, single user, checkbox); Calendar (month/week, optional end date, drag to reschedule); Timeline with swimlanes, and Gantt-style dependency arrows from a self-link field; List (collapsible grouped outline). Shared config: nested filters (3 levels, all operators per type, relative dates, "me"), sorts, up to 3 group levels, hide/reorder/resize fields, frozen columns, row height, row colouring (by select or conditions), summary bar aggregations, personal views, locked views, duplicate view, CSV export.

**Automations.** Triggers: record created; record updated (optionally specific fields); record matches conditions; form submitted; schedule (cron, timezone aware); incoming webhook. Actions: create record, update record, send email (SMTP), HTTP request (SSRF-guarded), in-app notification. Run history with logs, retries for transient failures, durable queue in SQLite.

**API.** Airtable-compatible REST v0 shape under `/api/v1` (list with `pageSize`/`offset`/`view`/`fields[]`/`sort`/`filterByFormula`/`maxRecords`, get, create, update PATCH/PUT, delete, `typecast`; metadata endpoints) so existing Airtable clients and n8n/Make/Zapier-style HTTP steps work by changing the base URL. Token rate limit 5 req/s per token like Airtable.

**Import/export & ops.** CSV import (new table with type inference, or into an existing table with column mapping); CSV export of any view; daily automatic backups with retention; `opengrid backup` / `opengrid restore`; automatic pre-migration snapshot; trash with 30-day retention; record history retention; health endpoint; single static binary, Docker image, docker-compose with Caddy, systemd unit.

### CUT (with reasons)

| Cut | Reason |
|---|---|
| Interface designer (dashboards, page builder, portals) | A second full app-builder product; would roughly double frontend scope. Views + forms + share links cover the small-business need. |

| AI features (Omni, AI fields, field agents) | Depend on external paid model APIs; not a self-contained feature. The REST API lets users bring their own AI tooling. |
| Sync (cross-base, external sources) and vendor integrations (Slack, Gmail, Jira, Salesforce…) | External-service dependent and fragile. Generic webhook + HTTP request + SMTP cover most of it. |

| SSO (SAML/OIDC) | Real configuration and support burden for a ≤25-user deployment; password + TOTP 2FA is solid. Revisit on demand. |
| Field-level and table-level edit permissions | Adds a permission check to every write path and every UI editor; five roles plus base-level sharing cover small teams. Revisit after v1. |
| S3/object storage, multi-node, Postgres | Each adds a moving part; single node + local disk + backups is the design. |
| Excel (.xlsx) import, Airtable-base importer | CSV covers the need for v1 (Airtable and Excel export CSV). |
| Airtable-style cursor webhooks API | Automations' "record created/updated → HTTP request" covers outbound notifications. |
| Presence avatars / live cursors | Low value; needs client→server presence channel. |
| Localization (non-English UI, `SET_LOCALE` output) | Translation infrastructure is ongoing maintenance; English only. |
| Native mobile apps, offline mode | Responsive web UI only. |
| Timeline resource-utilization, Gantt critical path & auto-shifting dependencies | Fiddly scheduling math with little small-business value; arrows + red invalid dependencies are kept. |
| Calendar iCal feed | Cut from v1 for scope; small and could come later. |
| Conditional lookups/rollups, lookup sort/limit | Stretch: build only if the core lookup/rollup path is done and solid. |

## 3. Architecture

```
crates/
  core/    og-core   pure Rust, no I/O; DTOs exported to TypeScript via ts-rs
           field.rs  view.rs  value.rs  limits.rs   (contracts, written)
           cell.rs   query.rs                       (W2)
           formula/  (lexer, parser, types, eval, functions, dates)  (W1)
           deps.rs   field dependency graph + cycle detection         (W6)
           api/      DTOs shared by server and web, one file per area
  server/  opengrid  axum binary + lib
           db.rs (writer + reader pool, migrations)  auth/  perm.rs  events.rs
           store/    sync business logic over rusqlite (tx in, Result out)
           engine/   recompute.rs (materialization), query.rs (view queries + cache)
           api/      thin handlers, one file per area, each exposes router()
           web.rs    serves the embedded web/dist
           tasks.rs  background jobs (sessions, trash, history, backups, volatile formulas, automations)
           backup.rs  cli.rs  config.rs
           migrations/0001_init.sql
           tests/    integration tests through the real router (tests/common harness)
web/       React + TypeScript SPA (Vite); src/api/types is generated by ts-rs; e2e/ Playwright tests
deploy/    Dockerfile, docker-compose.yml + Caddyfile, opengrid.service
docs/      plans, research, self-hosting guide
```

**Request flow.** Handler extracts `Actor` (session cookie or bearer token) → `db.read`/`db.write` closure → `perm::require_base(conn, actor, base_id, Role::X)` → `store::*` / `engine::*` → commit → `events.publish` → JSON response. All writes happen in one transaction on the single writer connection, including link-inverse maintenance, recompute cascades and history rows.

**Permissions.** `perm.rs` is the only authorization path. Viewer < Commenter < Editor < Creator < Owner. No access → 404 (no existence leaks); insufficient role → 403. Read-only tokens cap at Viewer; token base lists restrict reach; tokens cannot manage workspaces, tokens, or admin. Instance admins get no implicit data access.

**Error format.** `{"error": {"code": "...", "message": "..."}}`; internal errors are logged and returned generically.

### 3.1 HTTP API contract (internal API used by the web client)

All JSON. Cookie-authenticated unsafe requests need `X-OpenGrid-CSRF: 1`. Clients send `X-Client-Id` so SSE echoes can be skipped.

**Response conventions** (enforced by the live contract tests in `web/contract`, which run the TypeScript client against the real server and check every response against the generated types):

- Lists are bare JSON arrays of the DTO (`SessionInfo[]`, `TokenInfo[]`, `InviteInfo[]`, `AdminUser[]`, `BackupInfo[]`); a wrapper object exists only when it carries more than the list (`NotificationsResponse`, `AuditPage`).
- Creates answer `201` with the created DTO (`CreatedToken`, `CreatedInvite`, `AdminCreatedUser`); `DELETE` answers `204` with no body; `PATCH` answers the updated resource; actions with no result answer `{"ok": true}` (`OkResponse`: logout, password change, password reset request/confirm, revoke other sessions).
- `signup`, `GET|PATCH me`, `2fa/enable` and `2fa/disable` return `User`; `login` and `login/2fa` return `LoginResponse`; `invites/by-token/{token}/accept` returns the accepted `InviteInfo`.
- `GET /api/admin/audit?before=<id>&limit=<n>` is cursor-paged (newest first) and returns `AuditPage {entries, next_before}`.
- Every error, including malformed JSON or query strings (`crate::extract::{ApiJson, ApiQuery}`, mandatory in handlers; `axum::Json`/`Query` are never used to read a request, which a test enforces), unknown routes and wrong methods, is `{"error": {"code", "message"}}`.
- Deletes of schema objects (workspaces, bases, tables, views, members, automations) answer `200 {"ok": true}`; deleting a field answers `{"ok": true, "deleted_field_ids": [...]}` because it can cascade. Deleting records, comments, invites and tokens answers `204`.
- **Record writes** all answer with the records they touched, in request order: create `201 RecordsResponse`, `PATCH` update `200 RecordsResponse` (every patched record, changed or not), restore `200 RecordsResponse` (the restored records), move `200 RecordsResponse` (the moved records; duplicates in the request collapse to the first mention). `DELETE /api/tables/{id}/records {ids}` answers `204` with no body: a batch is all-or-nothing (any id that is not a live record of the table fails the whole request with 404 and deletes nothing; duplicate ids are ignored), so the deleted ids are exactly the ones sent.
- **Record shape.** `Record.values` is keyed by field id and holds every non-empty field. Computed fields (formula, lookup, rollup, count) hold their materialized value. **System fields** (autonumber, created time/by, last modified time/by) are in `values` under their own field ids whenever the table has such a field, in every response that returns records (create, update, get, view query); the same data is on the record as `autonumber`, `created_at`, `created_by`, `updated_at`, `updated_by`. Link values are `[{id, name}]`. Button fields hold the result of their `url_formula` (the materialized URL) as a plain string in `values`, kept current like any computed field and ready to open (only http(s) and mailto URLs should be opened); clients never evaluate button formulas themselves.
- **Group headers.** In a grouped view, `QueryResponse.groups` lists *every* group of the whole result on *every* page, in display order, depth-first; `start` and `count` always refer to the full ordered result, never to the page (so a page that shows only part of a group, or none at all, still gets all headers). Ungrouped views return `[]`.

- **Setup/auth** `GET /api/setup` → `{needs_setup, open_signup, email_enabled}`; `POST /api/auth/signup {email,name,password,invite_token?}`; `POST /api/auth/login {email,password}` → `{user}` or `{two_factor_required: true}`; `POST /api/auth/login/2fa {code}`; `POST /api/auth/logout`; `GET|PATCH /api/auth/me`; `POST /api/auth/password {current_password,new_password}`; `POST /api/auth/password-reset/request {email}`; `POST /api/auth/password-reset/confirm {token,new_password}`; `POST /api/auth/2fa/setup|enable|disable`; `GET /api/auth/sessions`, `DELETE /api/auth/sessions/{id}`, `POST /api/auth/sessions/revoke-others`.
- **Tokens** `GET|POST /api/tokens`, `DELETE /api/tokens/{id}`.
- **Invites** `POST|GET /api/workspaces/{id}/invites`, `POST|GET /api/bases/{id}/invites`, `DELETE /api/invites/{id}`, `GET /api/invites/by-token/{token}` (public), `POST /api/invites/by-token/{token}/accept`.
- **Admin** `GET|POST /api/admin/users`, `PATCH /api/admin/users/{id}`, `POST /api/admin/users/{id}/reset-link`, `GET /api/admin/audit`, `GET /api/admin/stats`, `GET|POST /api/admin/backups`, `GET /api/admin/backups/{name}`.
- **Workspaces** `GET|POST /api/workspaces`, `PATCH|DELETE /api/workspaces/{id}`, `GET /api/workspaces/{id}/members`, `PATCH|DELETE /api/workspaces/{id}/members/{user_id}`.
- **Bases** `POST /api/workspaces/{id}/bases`, `GET|PATCH|DELETE /api/bases/{id}` (GET returns full schema: tables, fields, views visible to caller, and caller role), `POST /api/bases/{id}/duplicate`, `GET /api/bases/{id}/collaborators`, `GET /api/bases/{id}/members`, `PATCH|DELETE /api/bases/{id}/members/{user_id}`.
- **Tables/fields/views** `POST /api/bases/{id}/tables`, `PATCH|DELETE /api/tables/{id}`, `POST /api/tables/{id}/duplicate`; `POST /api/tables/{id}/fields`, `PATCH|DELETE /api/fields/{id}`, `POST /api/tables/{id}/primary-field`; `POST /api/tables/{id}/views`, `PATCH|DELETE /api/views/{id}`, `POST /api/views/{id}/duplicate`.
- **Records**
  - `POST /api/views/{id}/query {offset?, limit?, search?, range?, timezone?, transient?}` → `QueryResponse {total, offset, records, groups, colors}`. `limit` defaults to 100 and is capped at `MAX_PAGE_SIZE`; `limit: 0` is a count-only request. `search` is a case-insensitive substring match over the view's visible (not hidden) fields. `range` `{field_id, end_field_id?, from, to}` (dates `YYYY-MM-DD`) keeps records whose date span overlaps it. `timezone` (IANA) is the viewer's zone for relative-date filters (default: the user's profile zone, then UTC). `transient` is the per-request override below. Viewer role; personal views of other users answer 404.
  - **Transient override** `transient: {filter?, sorts?, groups?}` (`TransientConfig`): for users who cannot save the view (viewers of shared views, editors of locked views). Each part present replaces the saved one for this request only (`sorts: []` / `groups: []` clear them; to drop the saved filter send a filter with no items); parts left out keep the saved value. It is validated with the same semantics as saving a view config (unknown fields, operators that do not suit a field's type, level limits) and a violation is a `400` whose message starts with `transient:`. It is never stored. The query cache is keyed by the effective config, so an override gets its own cache entries and a write invalidates them like any others.
  - `GET /api/views/{id}/aggregations?timezone=&search=&transient=` → `AggregationsResponse {values}` (field id → value for the view's configured summaries). The summaries cover the records that pass the view filter. `search` applies the same search as the query (only matching records are summarised). `transient` is the JSON-encoded override (only its `filter` matters here; at most 16 KB, URL-encode it); a malformed or invalid one is a `400`. The date `range` of a query does not apply.
  - `GET /api/tables/{id}/records/{rid}` → `Record` (404 for trashed records).
  - `POST /api/tables/{id}/records {records: [{values}], typecast?, after_record_id?, before_record_id?}` → `201 RecordsResponse`. New records go to the end of the manual order, or right after `after_record_id`, or right before `before_record_id`; giving both is a `400`, and so is an anchor that is not a live record of the table. Several new records keep their request order.
  - `PATCH /api/tables/{id}/records {records: [{id, values}], typecast?}` → `RecordsResponse`; `DELETE` (body `{ids}`) → `204`; `POST .../restore {ids}` and `POST .../move {ids, before_id? | after_id?}` → `RecordsResponse` (see conventions). Batches are all-or-nothing and capped at `MAX_RECORDS_PER_BATCH`.
  - `GET /api/tables/{id}/records/lookup?q=&limit=&view_id=` (link picker, Viewer) → `LinkCandidates {records: [{id, name}]}`: live records whose primary text contains `q` (case-insensitive), in manual order, at most `limit` (default 20, max 100), optionally restricted to the filter of `view_id` (a view of that table; otherwise 400).
  - `GET /api/records/{id}/history?before=&limit=` (Viewer) → `HistoryEntry[]`, newest first. `before` is the id of the last entry of the previous page, `limit` defaults to 50 (1 to 200). `changes` is `{field_id: {old, new}}` for the editable fields that changed. For **link fields** both sides are `[{id, name}]` with names resolved when the history is read (the current primary text of the linked record); a linked record that is in the trash or gone shows its id as the name. Other fields hold the canonical stored value.
  - `GET /api/records/{id}/comments` → `Comment[]` oldest first (Viewer); `POST` `{body}` → `201 Comment` (Commenter); `PATCH /api/comments/{id} {body}` → `Comment` (author only); `DELETE /api/comments/{id}` → `204` (author or base Owner). Bodies are plain text; mentions are written `@[Name](usrXXXX)` and notify the mentioned users who can read the base. Every change publishes a `comments_changed` event.
- **Formula check** `POST /api/tables/{id}/formula/check {expression, record_id?}` (Editor) → `FormulaCheckResult {ok, error?: {message, pos?}, result_type?, preview?}`: parses and type-checks a formula as typed (`{Field Name}` references) and previews it on `record_id` (default: the table's first record). It models formulas, not rollup expressions (those run over `values`; they are validated when the field is saved).
- **Trash** `GET /api/bases/{id}/trash` (Creator), `GET /api/workspaces/{id}/trash` (Owner; trashed bases), `POST /api/trash/restore {kind,id}` → `RestoreResponse {ok, restored_field_ids}` (restoring a field brings back the fields trashed with it; a link pair is listed once, under whichever side sorts first). `DELETE /api/fields/{id}` answers `DeleteFieldResponse {ok, deleted_field_ids}`. A trashed workspace cannot be listed (its trash listing is gone with it) but its owner can restore it by id.
- **Events** `GET /api/bases/{id}/events` (SSE, `og_core::api::events`).
- **Files** `POST /api/bases/{id}/attachments` (multipart) → `AttachmentRef`; `GET /api/attachments/{id}/{filename}`; `GET /api/attachments/{id}/thumb`.
- **CSV** `GET /api/views/{id}/export.csv`; `POST /api/tables/{id}/import`; `POST /api/bases/{id}/import`.
- **Sharing** `GET|POST /api/views/{id}/shares`, `PATCH|DELETE /api/shares/{id}`; public: `GET /api/public/shares/{token}`, `POST /api/public/shares/{token}/query`, `POST /api/public/forms/{token}/submit`, `POST /api/public/forms/{token}/attachments`.
- **Automations** (details in `docs/automations.md`)
  - `GET /api/bases/{id}/automations` → `Automation[]`; `POST` `CreateAutomation {name, enabled?, trigger, actions}` → `201 Automation`. A webhook trigger's token is returned **once**, in `Automation.webhook_token` of the create response (or of a `PATCH` with `rotate_webhook_token: true`); it is never readable again.
  - `GET /api/automations/{id}` → `Automation`; `PATCH` `UpdateAutomation` → `Automation`; `DELETE` → `200 {ok: true}`. Creators (and owners) list, read, write, test and delete definitions; Editors and above read the run history.
  - `GET /api/automations/{id}/runs?limit=&before=` → `RunsPage {runs, total, next_before}`, newest first; `before` is the id of the last run of the previous page, `limit` defaults to 50.
  - `POST /api/automations/{id}/test {record_id?, body?, dry_run? = true}` → `TestResult {dry_run, status, log, error?, run_id?}`; a dry run sends and writes nothing.
  - `POST /api/hooks/{token}` (public, JSON body up to 1 MB) → `202 WebhookAccepted {ok, run_id}`; unknown tokens and disabled automations answer 404; rate limited.
  - Actions that write records (`create_record`, `update_record`) go through the record write engine exactly like API writes (typecast, links, recompute, history) with source `automation`; their events are published after commit, so SSE clients and cached view queries see them. Records written by an automation never fire record triggers.
- **Notifications** `GET /api/notifications` (no parameters) → `NotificationsResponse {notifications, unread}`: the caller's 50 newest, newest first, plus the total unread count. `POST /api/notifications/read {ids?}` → `OkResponse`; an empty or missing `ids` (or no body) marks everything read, ids of other users are ignored. Kinds: `mention`, `assigned`, `invite`, `automation`.
- **Airtable-compatible** `/api/v1/...` (bearer tokens only), documented in `docs/api.md`.

Record JSON in responses: `{id, created_at, updated_at, created_by, updated_by, autonumber, values: {field_id: value}}`. Link values are returned as `[{id, name}]` (name = linked primary field text) and accepted as ids or `{id}` objects. User values are user ids (the client resolves names from `/collaborators`).

## 4. Workstreams

Each workstream is executed by a subagent in its own git worktree and merged by the orchestrator, who runs the full test suite after each merge. Every workstream starts with tests (`testing-first`) and ends with `cargo test` green for its crate plus `cargo clippy -- -D warnings`. Shared touchpoints (module lists, router merge list, dependency list, schema) were pre-created in the foundation commit so parallel work merges cleanly; new migrations are numbered by the orchestrator at merge time.

### Wave 1 (parallel)

**W1 core-formula** — `crates/core/src/formula/**`
- Intent: Airtable-compatible formula language: lexer, Pratt parser (case-insensitive functions, `{Field Name}` refs, `&`, comparison, unary minus, string escapes), reference rewriting (names ↔ ids), static result-type inference, evaluator with all 84 functions, Moment-style date formatting/parsing, timezones, error propagation, recursion/size limits.
- Interfaces: `parse(&str) -> Result<Expr, FormulaError>`; `referenced_fields(&Expr) -> Vec<FieldRef>`; `to_storage(src, &dyn Fn(&str)->Option<FieldId>) -> Result<String>` and `to_display(stored, &dyn Fn(&FieldId)->Option<String>) -> String`; `infer_type(&Expr, &dyn TypeEnv) -> Result<ResultType>`; `eval(&Expr, &dyn EvalContext) -> Value`; `is_volatile(&Expr) -> bool`. `EvalContext` provides field values by id, record id, created/modified time, `now`, default timezone.
- Check: `cargo test -p og-core formula` with ≥1 test per function plus property tests (parse never panics on arbitrary input; `to_display(to_storage(x)) == x` modulo whitespace).
- Risks: Airtable blank semantics (blank in arithmetic = 0, in concatenation = ""), date math across DST, `DATETIME_FORMAT` token coverage.

**W2 core-cells** — `crates/core/src/cell.rs`, `crates/core/src/query.rs` (+ submodules)
- Intent: per-type validation/normalization of client input into canonical stored JSON (lenient: numbers from strings, selects by name or id, many date formats, booleans); stored JSON → `Value`; display text (CSV export, search, primary names); text → value parsing (paste, CSV import); type conversion between all field types; filter evaluation for every operator × type including relative dates and "me"; sort comparators per type (selects sort by choice order, blanks last ascending); grouping keys; full-text search matching; summary-bar aggregations; validation of filter/sort/group configs against a field set.
- Check: `cargo test -p og-core cell query` with a conversion matrix test over all type pairs and operator × type tests.
- Risks: timezone handling for date-only vs instants; locale-free number parsing.

**W3 server-auth** — `crates/server/src/api/{auth,admin,tokens,invites}.rs`, `src/auth/totp.rs`, `src/email.rs`, `src/store/{users,invites,tokens,audit}.rs`, `crates/core/src/api/auth.rs`, `tests/auth*.rs`
- Intent: every endpoint in §3.1 Setup/auth, Tokens, Invites, Admin (except backups). Rate limits, audit log entries, timing-safe login, session revocation on password change/deactivation, email sending (no-op + log when SMTP unset).
- Check: integration tests covering success and failure paths: first-user admin, invite-only enforcement, wrong password, rate limiting, 2FA flow, token scopes, deactivated user locked out immediately, admin-only endpoints reject non-admins.

**W4 ops** — `crates/server/src/{backup,tasks}.rs`, `src/api/attachments.rs`, `src/store/attachments.rs`, `src/api/admin_backups` route (inside `admin.rs` is W3's; W4 adds `api/backups.rs`), `deploy/**`, `scripts/**`, `README.md`, `docs/self-hosting.md`
- Intent: backup/restore archives, scheduled backups with retention, pre-migration snapshot, background task runner skeleton (session purge, trash purge, history retention), attachment storage (streamed upload, SHA-256 content addressing, size limit, image thumbnails with decode limits, safe download headers), Dockerfile (multi-stage, static musl binary, non-root), docker-compose with Caddy, systemd unit, `scripts/check.sh`.
- Check: tests for backup→restore round trip, retention pruning, attachment upload/download/permission/limits/content-type safety; `docker build` succeeds.

**W5 web-shell** — `web/**` (React + TypeScript), ts-rs derives in `crates/core`, `crates/server/src/web.rs`
- Intent: Vite + React 19 + TS scaffold, ts-rs type generation (`cargo test -p og-core export_bindings` writes `web/src/api/types/`), API client (CSRF header, X-Client-Id, typed errors, 401 → login), SSE helper, TanStack Query setup, design system (Tailwind v4 + Radix components, light/dark), auth pages (setup, login, 2FA, signup with invite, invite accept, forgot/reset password), home (workspaces + bases), base shell (table tabs, view sidebar, ViewHost extension point), account (profile, password, 2FA with QR, sessions, tokens), admin (users, audit, stats, backups).
- Check: `npm run build` and `npm test` (Vitest) pass; `tsc --noEmit` clean; the server serves the built app with no CSP violations.

### Wave 2

**W6 data-plane** — `crates/core/src/deps.rs`, `crates/core/src/api/{workspaces,schema,records}.rs`, `crates/server/src/store/{workspaces,bases,tables,fields,views,records,links,history,comments,trash}.rs`, `crates/server/src/engine/{recompute,query}.rs`, `crates/server/src/api/{workspaces,bases,tables,fields,views,records,comments,trash,events}.rs`, tests

### Wave 3 (parallel, after W6)

- **W7 sharing+csv+v1** — `api/{sharing,csv,v1}.rs`: share links, public view/form endpoints (rate-limited), CSV import/export, Airtable-compatible API. Check: tests incl. Airtable response shapes and `filterByFormula`.

### Wave 4 — refine, test, review (loop until clean)

## 5. Testing strategy

- **og-core:** unit + property tests (proptest) for formulas, conversions, filters, sorts. Pure functions → exhaustive.
- **server:** integration tests drive the real router in-process (`tests/common`): every endpoint's success path, auth failure, role matrix, validation errors. Store/engine functions get direct tests against a temp DB.
- **migrations:** test applying all migrations to an empty DB, idempotency, refusing newer schemas, FK integrity.
- **web:** Vitest + Testing Library for helpers and components; behaviour via Playwright E2E.
- **E2E:** opt-in (`OPENGRID_E2E=1 cargo test -p og-e2e`) because it needs Chrome.
- **Definition of done** for any claim: a test exists and passes. Reports distinguish tested from written-only.
